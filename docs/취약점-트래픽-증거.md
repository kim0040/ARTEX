# 발견에 트래픽 증거를 여러 개 묶기

발견 상세의 「연결한 트래픽」은 여러 페이지에서 고르고, 용도와 설명을 달고, 순서를 바꾸고, 연결을 끊을 수 있습니다. 트래픽 페이지에서도 기록을 여러 개 골라 이미 있는 발견 하나에 한 번에 연결합니다. 다른 작업에서 물려 받은 발견의 증거는 읽기 전용입니다. 고치려면 그 증거가 생긴 작업으로 들어갑니다.

이 기능이 있는 이유: 트래픽 목록은 지워도 되는 작업 기록이고, 발견 보고서는 그 기록이 사라져도 남아야 하는 증거입니다. 그래서 원본 트래픽과 분리된 스냅샷을 `evidence`에 둡니다. 자산 그래프나 탐색 그래프의 노드를 바꾸는 기능이 아니라, 탐색 그래프의 발견 노드에 "그때 오간 HTTP"를 붙여 두는 저장입니다.

시스템 설정의 「에이전트가 트래픽을 자동으로 연결」은 기본이 꺼져 있습니다. 읽고 쓰는 곳은 `/api/settings`의 `agent_traffic_binding`입니다. 켜면 요청·응답, 도구 호출, 프롬프트를 더 읽어서 토큰을 더 씁니다. 다음 라운드의 에이전트부터 새 설정을 봅니다. 꺼져 있으면 자동 연결 인자와 나중에 잇는 도구를 숨기고, 자동 연결 안내를 넣지 않으며, 이미 돌아가던 세션이 새로 내는 자동 연결은 거절합니다. 사람이 직접 연결하는 것, 트래픽을 캡처하는 것, 저장해 둔 증거를 읽고 내보내는 것은 그대로입니다.

켜져 있을 때의 기본 흐름은 「발견을 저장 → 보고서 에이전트를 자동으로 부름 → 트래픽을 대조해 연결 → 최신 증거 버전으로 보고서를 씀」입니다. 올린 쪽은 `evidence`에 확인에 쓴 명령, 중요한 출력, 이미 있는 실제 트래픽 ID와 용도를 남깁니다. 보고서 에이전트는 발견 상세와 실행 기록을 보고 `traffic_search` / `traffic_get`으로 확인한 뒤 `bind_finding_traffic`을 호출하고, 최신 `version`을 읽어 보고서를 저장합니다. 스위치가 꺼져 있으면 보고서 에이전트는 원본 트래픽을 검색·조회하는 도구를 추가로 받지 않고 자동으로 연결하지도 않습니다. 사람이 연결해 둔 스냅샷은 읽고 보고서는 쓸 수 있습니다.

이미 있는 호출과의 호환: `report_finding`의 `traffic_refs` / `evidence_hint_id`로 그 자리에서 연결할 수 있습니다. 연결은 선택입니다. TCP처럼 HTTP가 아닌 경우, 수집하지 못한 경우, 정확히 맞는 기록이 없는 경우에는 참조를 빼도 보고와 보고서 작성은 됩니다. 명령 출력이나 로그 같은 다른 확인 가능한 증거를 남기고, 왜 연결하지 않았는지 적는 편이 좋습니다. 새 필수 필드는 없습니다. 넘긴 ID는 모두 유효하고 본문이 완전해야 합니다. 하나라도 실패하면 이번 연결은 롤백됩니다. 보고와 함께 명시적으로 연결하다 실패하면 보고 전체가 롤백됩니다. 같은 스냅샷을 다시 추가해도 연결이 늘지 않고, 설명을 덮어쓰지도 않습니다.

## 에이전트 번호와 보고서 버전

`report_finding`에 선택 인자가 있습니다. 배열 순서가 처음 증거 순서입니다.

```json
{
  "traffic_refs": [
    {"traffic_id": "실제 트래픽 ID", "role": "baseline", "note": "정상 계정 요청"},
    {"traffic_id": "다른 실제 트래픽 ID", "role": "proof", "note": "재현 요청"}
  ]
}
```

용도는 `baseline`(정상 대조), `proof`(발견을 보여 주는 기록), `verification`(추가 확인), `supporting`(보조, 기본값)입니다. 먼저 `traffic_search` / `traffic_get`으로 실제 기록을 확인합니다. 도메인과 시각은 후보를 거르는 데만 쓰고, 어느 작업 것인지를 단정하지 않습니다.

반환 첫 줄은 여전히 `finding recorded: <탐색 노드 ID>`입니다. 이어서 JSON에 독립 발견 기록 `finding_id`, 탐색 노드 `finding_node_id`, 연결 요약이 있습니다.

- `get_finding_traffic(finding_id)`는 **독립 발견 기록 ID**를 씁니다. 순서 있는 목록과 `version`을 돌려줍니다. `binding_id`, `side=request|response`, `offset`, `length`로 나눠 읽을 수 있고, 한 조각은 최대 8192바이트입니다.
- `update_finding_report`의 `finding_id`는 **계속 탐색 노드 ID**입니다. `evidence_version`에는 실제로 읽은 버전을 넣습니다. 보고서를 만드는 동안 증거가 바뀌면 옛 버전 저장은 거절되므로, 다시 읽고 다시 써야 합니다.
- 옛 보고서 호출이 버전을 안 넘기면, 이미 있는 트래픽 증거를 덮어썼다고 말하지 않습니다. 연결, 설명, 용도, 순서가 바뀌면 기존 보고서는 업데이트가 필요하다고 표시됩니다.

자동 연결이 켜져 있으면 `add_hint` / `add_task_hint`는 힌트 하나 또는 `hints` 배열의 각 원소에 `traffic_refs`를 넣을 수 있습니다. 플래너가 대신 보고할 때는 `evidence_hint_id`로 이 작업의 해당 힌트에 있는 참조를 집습니다. 물려 받은 힌트의 참조는 쓸 수 없습니다. 도메인, 시각, 둘러본 기록으로 연결을 추측하지 않습니다. 제출이 실패하면 발견의 일부만 만들거나 보고서 에이전트를 미리 부르지 않습니다.

이미 있는 발견에 연결이 빠졌으면 `bind_finding_traffic(finding_id, traffic_refs)`로 나중에 잇습니다. 발견을 다시 등록하지 않아도 됩니다. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail`은 `finding_id`와 `finding_node_id`를 분명히 돌려줍니다. 예전 `id`는 탐색 노드라는 뜻을 유지합니다.

시작할 때 옛 도구 스키마에는 선택 속성만 더합니다. 원래 기본 트래픽 도구 연결은 보고서 에이전트까지 넓어지고, 나중에 잇는 도구는 기본적으로 보고서 에이전트에게 갑니다. 사람이 바꿔 둔 연결 목록, 프롬프트, 설명, 켜짐 상태는 유지됩니다. 안내는 도구를 모두 조립한 뒤에 한 번에 붙입니다. 보고하는 역할은 이미 있는 증거를 넘기고, 보고서 에이전트는 대조, 연결, 보고서 작성을 맡습니다. 플랫폼 대화에 작업 문맥이 없으면 구조화된 힌트로 작업 에이전트에게 넘기고, 그 자리에서 보고하지 않습니다. 작업이 끝났다고 보기 전에 이미 있는 증거를 넘깁니다. 패킷이 없다고 억지로 기다리지는 않습니다. 실패한 `report_finding`은 보고서 에이전트를 부르지 않습니다.

## API

기본 경로는 `/api/exploration/findings/{finding_id}/traffic`이고, 독립 발견 ID를 씁니다. 인증은 다른 API와 같습니다. `context_task`가 작업을 볼 수 있는지, 물려 받은 항목이라 읽기 전용인지를 확인합니다.

| 메서드 / 상대 경로 | 요청 / 반환 |
| --- | --- |
| `GET` | 순서 있는 요약, 증거 버전, 보고서가 채택한 버전 |
| `POST` | `{"traffic_refs":[...]}` 를 한 묶음으로 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"설명"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}` 전체 목록이어야 함 |
| `GET /{binding_id}` | 스냅샷 메타데이터와 길이가 제한된 본문 미리보기 |
| `GET /{binding_id}/body` | `side`, `offset`, `length`. `download=1`이면 원본 바이트 전체 |

버전이나 순서 집합이 충돌하거나, 아카이브 중에 쓰면 `409`입니다. 물려 받은 항목에 쓰면 `403`입니다. 없거나 그 발견의 연결이 아니면 `404`입니다. 트래픽·첨부를 읽거나 검사가 실패하면 오류를 분명히 돌려줍니다.

## 저장과 이전

켜질 때 PostgreSQL을 멱등으로 바꿉니다. `traffic_evidence_snapshots`, `finding_traffic_bindings`가 생기고, `findings.evidence_version` / `report_evidence_version`(기본 0)이 붙습니다. 예전에 적힌 글을 보고 연결을 추측해 채우지는 않습니다.

스냅샷은 원래 트래픽 ID, 수집 시각, URL, 메서드, 상태, 요청·응답 헤더, 본문 길이, SHA-256을 저장합니다. 본문은 해시로 `<data>/evidence/blobs/<앞 두 글자>/<hash>.bin`에 둡니다. 지워도 되는 `data/traffic`과는 따로이고, 여러 발견이 스냅샷과 본문을 공유할 수 있습니다. 스냅샷 내용을 고치는 API는 없습니다. 검사가 안 맞으면 읽기와 내보내기가 실패합니다.

원래 트래픽의 쓰기 잠금 아래에서 본문 전체를 읽습니다. 큰 본문 블롭과 옛 디렉터리 기록도 포함합니다. 먼저 파일을 저장하고 검사한 다음, PostgreSQL 트랜잭션 하나로 탐색 노드, 의도 관계, 발견, 스냅샷, 연결을 씁니다. 커밋된 뒤에야 플래너에게 알립니다. 실패하면 아무도 가리키지 않는 파일이 남을 수 있지만, 업무 기록이 반쪽만 생기지는 않습니다.

PostgreSQL 권고 잠금 `7337741004`가 증거 파일과 SQL 참조를 맞춥니다. 작업 행 잠금은 아카이브 대기 이후의 증거 수정을 막습니다. 복구는 본문을 설치하는 때부터 메타데이터 커밋까지 증거 잠금을 잡습니다. 발견을 지우면 연결도 함께 지워집니다.

청소기는 한 시간에 한 번 돌고, 아무도 가리키지 않으며 진행 중인 작업이 아닌 내용만 거둡니다. 최소 24시간은 기다립니다. 일반 트래픽 청소는 증거 디렉터리를 건드리지 않습니다. 뜨거운 데이터를 백업할 때는 PostgreSQL과 `data/evidence`를 같이 백업합니다.

## 내보내기와 아카이브

마크다운에는 순서가 있는 증거 목록과 버전이 들어갑니다. JSON에는 메타데이터가 들어갑니다. CSV에는 개수와 연결 ID가 추가됩니다. `md-zip`은 발견 마크다운을 남기고 다음을 넣습니다.

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

마크다운은 상대 링크로 메시지를 가리킵니다. 다운로드를 보내기 전에 첨부 복사, 해시 검사, 압축, 디스크 동기화, ZIP 항목 전체의 CRC 읽기 검사까지 끝냅니다. 빠지거나 깨지면 다운로드 전체가 실패합니다. 첨부 전체는 이진 원본 바이트를 유지합니다.

아카이브 v3는 발견의 연결 관계를 보고 스냅샷과 본문을 모읍니다. 원래 트래픽이나 도메인에 기대지 않습니다. 묶음 검사가 끝난 뒤에야 뜨거운 데이터를 지웁니다. 공유된 증거는 남습니다. 복구는 본문 설치를 먼저 검사하고, 그다음 트랜잭션으로 메타데이터와 연결을 되돌립니다. 실패하면 다시 시도할 수 있습니다. v1/v2도 복구할 수 있고, 없던 새 필드는 0으로 채웁니다.

## 확인과 경계

테스트 패키지마다 PostgreSQL 테스트 데이터베이스를 새로 두고 `ARTEX_PG_DSN`으로 지정합니다. 남아 있는 작업나 모델 픽스처가 백그라운드를 깨우지 않게 하려는 것입니다. 관련 패키지 테스트를 모두 돌리고, 설정이 없어 건너뛰는 일이 없는지도 봅니다.

```sh
# 패키지를 돌리기 전에 ARTEX_PG_DSN을 그 패키지 전용 테스트 데이터베이스로 둡니다. 설정을 명시했는데 실패하면 오류여야 합니다.
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

화면 쪽은 `npx tsc --noEmit`, 영향 받은 파일의 Biome, Webpack 빌드, `NEXT_EXPORT=1` 정적 내보내기입니다. 캐시 디렉터리는 따로 두어, 켜 둔 개발 서버를 덮지 않습니다.

이 컴퓨터에서의 끝에서 끝까지 확인은 포트를 따로 두고, 통제된 HTTP와 도메인 HTTPS 대상, 임시 데이터 디렉터리를 씁니다. 연결 입구 둘, 페이지를 넘는 선택, 순서와 설명, 오류 안내, 물려받은 항목의 읽기 전용, 다운로드, 그리고 원래 트래픽을 지운 뒤의 내보내기, 아카이브, 뜨거운 본문 회수, 복구와 해시 확인을 덮습니다.

이 기능의 첫 버전은 증거 전체를 하나의 잠금으로 맞춥니다. 연결이나 내보내기가 많거나 첨부 다운로드가 느리면 다른 증거 작업이 기다릴 수 있습니다. 기록이나 완전한 본문이 없으면 증거를 만들어 채우지 않습니다. 캡처 스위치를 바꾸지 않고, HTTPS로 IP에 직접 붙을 때의 인증서 문제도 다루지 않습니다.
